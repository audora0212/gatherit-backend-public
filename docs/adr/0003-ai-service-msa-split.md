# ADR 0003 — AI 추출 서비스 분리 제안

- 상태: 제안 (미구현)

## 맥락

일정 후보 추출은 외부 LLM 응답을 기다리는 작업입니다. 일정 및 그룹 API와 지연, 비용, 실패 특성이 다를 수 있어 별도 배포를 검토했습니다. 다만 그 차이가 실제로 독립 서비스 운영 비용을 정당화하는지는 측정이 필요합니다.

현재는 `AiScheduleService`와 `GeminiExtractor`가 같은 Spring Boot 애플리케이션 안에 있습니다. 추출 메서드의 외부 호출은 DB 트랜잭션 밖에서 수행하고, 선택한 후보의 등록은 기존 `EventService`를 호출합니다. 사용량 로그, 중복 확인, 등록 결과 영수증도 core의 저장소를 사용하므로 AI 패키지가 이미 독립 서비스 경계를 갖췄다고 보지는 않습니다.

## 제안의 범위

분리한다면 외부 추출 호출만 별도 서비스로 이동하는 방안을 우선 검토합니다.

| 소유자 | 책임 |
|---|---|
| 추출 서비스 | 입력을 받아 외부 모델을 호출하고 구조화된 일정 후보 반환 |
| 기존 API | 사용자 인증, 권한, 쿼터, 후보 검증과 중복 확인, 사용자 확인 후 일정 저장, 멱등 등록 결과 |

일정 DB와 최종 등록 트랜잭션은 기존 API에 남깁니다. 외부 추출 서비스가 일정 엔티티를 직접 저장하지 않게 하여 서비스 간 DB 쓰기 트랜잭션을 만들지 않는 방향입니다.

## 계약 초안

현재 구현의 입력 범위를 기준으로 텍스트 추출 계약부터 정의할 수 있습니다. 아래는 미구현 계약 초안입니다.

```text
request: sourceText, 기준 날짜, webSearch 허용 여부
response: 일정 후보, 출처, 모델 식별자, 토큰 사용량
```

계약 버전, 입력과 응답의 크기 제한, 서비스 간 인증, 타임아웃, 취소 전파, 재시도 시 과금과 중복 호출 정책을 확정해야 합니다. 같은 네트워크 안에 있다는 사실만으로 인증을 대체하지 않습니다. 서킷브레이커나 독립 서비스 메트릭은 현재 구현 완료 사항이 아닙니다.

사용자가 후보를 즉시 확인하는 현재 흐름에서는 동기 호출을 우선 검토할 수 있습니다. 다만 비동기 작업 상태를 보여주는 UX가 필요해지면 큐 방식도 다시 비교합니다. 어느 방식을 택해도 AI 실패 시 수동 일정 입력 경로는 유지합니다.

## 보류 이유와 재검토 조건

별도 서비스는 네트워크 실패, 계약 호환성, 배포와 롤백, 서비스 간 추적과 자격증명 관리를 추가합니다. 현재는 단일 배포를 유지하면서 외부 호출의 지연, 오류, 비용과 핵심 API 영향을 관측하는 편이 우선입니다.

재검토 근거는 추출 요청이 핵심 API의 자원을 지속적으로 점유하거나, 별도 동시성 및 쿼터 한도 또는 독립 배포가 필요한 경우입니다. 분리 전에 프로세스 내 호출 한도와 타임아웃 조정과 비교하고, 실제 이득을 확인할 테스트를 마련합니다. 추출 분리만으로 핵심 API의 쿼터 및 등록 경합까지 해결되는 것은 아닙니다.
