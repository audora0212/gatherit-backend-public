# 인덱스 효과라고 생각했지만 비교 조건이 달랐다

그룹 멤버십과 날짜 범위로 일정을 조회하는 쿼리를 로컬 MySQL과 합성 데이터로 비교한 기록이다.

## 첫 비교에서 놓친 것

대량의 합성 일정을 적재한 뒤 `start_at` 단일 인덱스와 `(start_at, end_at)` 복합 인덱스를 비교했다. 복합 인덱스를 만든 쪽에서 쿼리가 빨라져 인덱스 효과라고 생각했다.

그런데 다른 그룹 멤버십 조건으로 다시 측정하니, 기존 단일 인덱스의 baseline부터 앞선 결과와 달랐다. 원인을 추적하니 처음 비교에서는 복합 인덱스를 만든 쪽에만 `ANALYZE TABLE`을 실행했다. 인덱스와 옵티마이저 통계 상태라는 두 변수가 동시에 달라졌던 것이다.

## 다시 비교한 방법

양쪽 모두 통계를 갱신한 뒤 인덱스만 바꿔 비교했다. 멤버십 조건도 함께 바꿔 특정 데이터 분포에서만 이득이 있는지 확인했다. 응답 시간만 보지 않고 `EXPLAIN ANALYZE`의 구동 테이블, 스캔, 정렬 경로를 대조했다.

그 조건에서는 복합 인덱스가 추가 이득을 보여주지 않았다. 처음의 큰 차이는 대량 적재 이후 통계 상태와 실행계획 변화로 설명하는 편이 맞았다. 쓰기와 저장 비용을 추가할 근거가 부족해 복합 인덱스 추가를 철회했다.

현재 [Event 엔티티](../../src/main/java/com/gatherit/api/event/entity/Event.java)에는 `idx_events_start_at`이 있고 해당 복합 인덱스는 없다. 대상 조회는 [EventRepository](../../src/main/java/com/gatherit/api/event/repository/EventRepository.java)의 `findVisibleEventsInRange`에서 확인할 수 있다.

## 공개한 근거와 공개하지 않은 근거

이 저장소에서 확인할 수 있는 것은 현재 쿼리와 인덱스 선언과 판단 과정이다. 당시 합성 데이터와 전체 실행계획 원본을 재현 가능한 데이터셋으로 공개한 상태는 아니다. 그래서 이 문서에는 지연 시간이나 개선 배수를 성과 수치로 넣지 않았다.

다시 실험한다면 격리 MySQL에서 데이터 생성 규칙, DB 버전과 설정, 캐시 상태, 반복 횟수, 멤버십 조건을 고정하고 두 비교군의 통계를 동일하게 준비해야 한다. `EXPLAIN ANALYZE`의 실행 시간과 네트워크와 결과 전송을 포함한 API 응답 시간도 섞지 않아야 한다.

이 경험 이후에는 큰 개선폭이 나왔을 때 결과를 바로 채택하지 않고, baseline이 다시 나오는지부터 확인한다. 인덱스를 더한 결과만 아니라 추가하지 않기로 한 판단도 남기기로 했다.
