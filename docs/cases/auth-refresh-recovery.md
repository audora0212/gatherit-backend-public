# 토큰은 갱신됐는데 앱에는 저장되지 않았다

토큰 갱신 응답이 유실될 때 세션을 복구한 서버 측 사례다. 자동 테스트와 기기 검증의 범위를 구분했다.

## 사용자가 겪은 문제

앱을 백그라운드에 두었다가 다시 열면 로그인이 풀렸다는 제보가 있었다. 명시적인 로그아웃 기록만으로는 설명되지 않았다. 서버가 refresh token을 교체한 뒤 응답이 유실되거나 앱의 저장이 끝나지 않으면, 서버와 앱이 서로 다른 토큰을 보관할 수 있었다.

기존의 짧은 유예는 즉시 재시도에는 도움이 됐지만 다음 날 앱을 다시 여는 경우까지 다루지는 못했다. 그렇다고 이전 토큰을 오래 허용하면 새 로그인과 로그아웃의 의미가 달라진다.

## 무엇을 바꿨나

서버의 회전, 로그인, 로그아웃이 같은 사용자 행부터 잠그도록 순서를 맞췄다. refresh 행이 아직 없는 첫 로그인도 사용자 행 잠금으로 직렬화한다.

응답 유실 복구에는 앱이 회전 요청 전에 저장한 무작위 `refreshAttemptId`를 사용한다. 서버는 이전 토큰과 이 식별자를 함께 묶은 해시를 저장한다. 두 값을 다시 제시하면 같은 회전 시도의 재요청인지 확인하고, 이미 발급한 현재 refresh token을 반환한다. 재요청 때문에 다시 회전하거나 만료를 연장하지 않는다.

```text
앱: 이전 토큰 + 요청 식별자 저장
  → 서버: 토큰 회전 및 복구 증명 저장
  → 응답 유실
  → 앱: 같은 이전 토큰 + 같은 식별자로 재요청
  → 서버: 동일 시도 확인 후 현재 토큰 반환
```

복구 범위는 제한했다.

- 이전 토큰만 가진 요청에는 기존 grace 정책만 적용한다.
- 복구 창에는 상한이 있으며 이전 JWT와 현재 세션의 만료를 넘지 않는다.
- 새 로그인, 로그아웃, 다음 회전 이후에는 과거 복구 증명을 사용하지 못한다.
- 오래된 토큰 요청을 거절하더라도 현재 세션을 지우지 않는다.
- 세션을 명시한 지연 로그아웃은 나중에 만들어진 로그인 세션을 삭제하지 않는다. 본문 없는 구형 로그아웃 요청의 한계는 남는다.

관련 구현은 [RefreshTokenStore](../../src/main/java/com/gatherit/api/auth/service/RefreshTokenStore.java), [RefreshToken](../../src/main/java/com/gatherit/api/auth/entity/RefreshToken.java), [AuthService](../../src/main/java/com/gatherit/api/auth/service/AuthService.java)에 있다. 복구 정보는 nullable 열로 추가해 기존 행을 읽을 수 있게 했다. 새 코드를 적용할 때는 필요한 스키마가 먼저 준비되어 있어야 한다.

## 어떻게 확인했나

[RefreshTokenStoreIntegrationTest](../../src/test/java/com/gatherit/api/auth/service/RefreshTokenStoreIntegrationTest.java)는 실제 JPA 트랜잭션과 여러 스레드를 사용한다. Docker나 운영 계정 없이 격리 H2 DB에서 다음을 확인한다.

- grace 이후와 다음 날의 동일 시도 복구, 다른 식별자의 거절
- 복구 기간, JWT와 현재 세션의 만료 경계
- 동시 refresh가 같은 회전 결과를 받는지
- refresh와 로그아웃의 경합이 삭제된 세션을 부활시키지 않는지
- 새 로그인과 오래된 refresh 요청 및 지연 로그아웃 간의 경합에서 새 세션이 보존되는지
- 이전 토큰 형식을 새 토큰 형식으로 전환할 때의 호환성

```powershell
.\gradlew.bat test --tests "*RefreshTokenStoreIntegrationTest"
```

```bash
./gradlew test --tests '*RefreshTokenStoreIntegrationTest'
```

## 확인 범위와 남은 일

이 테스트는 H2에서 JPA와 잠금 동작을 검증한다. MySQL의 잠금, 격리, 대기 시간까지 검증한 결과로 쓰지 않는다. 별도의 격리 서버와 iOS Simulator에서 응답 유실 재시도를 확인했지만, 그것도 실제 OAuth 공급자와 모든 실기기 로그인 경로의 검증은 아니다.

기존 설치본 업데이트 후 로그인 유지, 실제 소셜 로그인, 장시간 백그라운드 복귀는 기기, 앱 빌드, 서버 버전을 구분해 별도로 확인해야 한다. 이 사례의 검증 결과만으로 현재 배포 바이너리나 모든 로그인 경로의 상태를 판단할 수는 없다.

복구 증명은 기기 바인딩이 아니다. 이전 토큰과 요청 식별자를 모두 탈취한 공격자를 원래 앱과 구별하지 못한다. 저장 위치, 복구 기간, 세션 폐기 조건을 함께 다뤄야 한다.

기존 사용자까지 로그아웃시키지 않도록 세션을 일괄 삭제하거나 서명 키를 교체하는 방식은 피했다.
